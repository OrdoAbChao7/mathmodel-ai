# 数学建模国赛论文生产框架设计

## 1. 目标

在项目内建设一个可持续复用的数学建模论文生产框架。用户既可以用自然语言要求 Codex 完成某个题目文件夹，也可以运行统一命令初始化、构建、审查和打包论文。框架不承诺自动替代建模判断，而是把题目理解、模型求解、结果验证、论文写作和 LaTeX 交付连接成一条可追溯、可恢复、可反复审稿的生产链。

框架的成功标准是：对新的预测、优化或评价类题目，能够创建标准工程；容纳题目专用求解代码；从结构化结果生成正文与图表；编译唯一版本的 PDF；输出机器可读质量报告；明确阻断不可复现、证据缺失、正文不足或依赖附录凑页数的论文。

## 2. 非目标

- 不用同一套固定算法自动解决所有赛题。
- 不把页数等同于质量，也不通过空白、字号、重复图表或附录堆叠满足页数。
- 不自动认定论文达到获奖等级；最终学术判断仍需人工审稿。
- 不复制 vendored 仓库中的获奖论文、代码或结论。
- 不在初始化时覆盖题目原始文件或已有工作目录。
- 不把未经验证的自然语言数字写入最终论文。

## 3. 使用入口

### 3.1 自然语言入口

`mathmodel-skill` 在以下请求中触发：完成一个题目文件夹、建立模型、生成或修改 CUMCM LaTeX 论文、审查数学建模论文、修复正文与附录比例、编译最终 PDF。Skill 负责研究判断、模型选择、题目专用代码、正文写作和人工审稿。

### 3.2 CLI 入口

统一入口为：

```powershell
python mathmodel-skill/scripts/mathmodel.py <command> <project>
```

首期命令：

| 命令 | 作用 |
|---|---|
| `init` | 在题目目录中创建标准工程和配置，不覆盖已有文件 |
| `adopt` | 将已有论文工程接入框架，生成配置和缺失契约文件 |
| `inspect` | 清点题目、附件、代码、数据和 LaTeX，记录哈希与数据概况 |
| `build` | 按配置执行分析、图表、LaTeX 编译与审查 |
| `audit` | 不重新求解，只审查当前结构化产物、源码和 PDF |
| `status` | 显示最近运行、阶段状态、阻断项和产物路径 |
| `package` | 仅在质量门禁通过后生成唯一命名的提交包 |

所有命令支持 `--json` 输出。`init` 遇到非空目录时只创建不存在的框架文件；文件冲突时退出并列出冲突。`adopt` 只新增框架元数据，不改写已有论文或求解脚本。

## 4. 分层架构

### 4.1 协调层：Skill

Skill 定义完整工作流、判断门槛、题型路由和人工审稿要求。它读取必要参考文件，调用 CLI 获取确定性证据，并编写题目专用分析代码和论文内容。

### 4.2 工具层：Python CLI

CLI 使用 Python 3.11 以上版本和标准库实现核心功能。Excel 深度统计可选用项目已声明的 `openpyxl`；缺少可选依赖时保留文件清单并发出 WARN，不影响初始化。PDF 元数据通过 `pdfinfo` 获取，页面渲染通过 `pdftoppm` 完成，LaTeX 通过 `xelatex` 编译。

### 4.3 题目层：项目适配代码

每道题在自身目录保存题目专用代码。框架只规定命令和产物契约，不把预测、优化或评价模型硬编码进 CLI。默认分析入口为 `analysis/run.py`，它必须读取只读原始输入，并输出结构化结果、验证结果、图表和注册表。

### 4.4 展示层：LaTeX 模板

模板来自当前 CUMCM 基线，采用拆分章节、统一图表风格和明确分页标记。模板不包含特定题目的数字。正文、参考文献和附录的边界可由 `.aux` 标签精确读取。

## 5. 标准项目结构

```text
problem-project/
├─ mathmodel.json
├─ problem/                       # 题目原文，只读使用
├─ data/
│  ├─ raw/                        # 原始附件，只读使用
│  └─ processed/                  # 代码生成的数据
├─ analysis/
│  ├─ run.py                      # 题目专用统一入口
│  ├─ models/                     # 题目专用模型
│  └─ tests/                      # 手算样例、边界和性质测试
├─ artifacts/
│  ├─ problem-map.json
│  ├─ data-audit.json
│  ├─ model-registry.json
│  ├─ result-registry.json
│  ├─ claim-registry.json
│  ├─ figure-registry.json
│  └─ validation.json
├─ paper/
│  ├─ main.tex
│  ├─ commons/
│  ├─ contents/
│  ├─ figures/
│  └─ tables/
├─ build/
│  ├─ paper.pdf
│  ├─ quality-report.json
│  ├─ quality-report.md
│  ├─ page-metrics.json
│  └─ previews/
└─ .mathmodel/
   └─ runs/<run-id>/manifest.json
```

原始题目和附件可以保留在项目根目录；配置通过相对路径引用它们。框架不得移动或重命名用户文件。

## 6. 配置契约

`mathmodel.json` 使用 UTF-8 JSON，首期模式如下：

```json
{
  "schema_version": 1,
  "project_id": "training-001",
  "title": "待求解题目",
  "contest": "CUMCM",
  "problem_type": "optimization",
  "inputs": {
    "statements": ["problem/problem.pdf"],
    "attachments": ["data/raw/attachment.xlsx"]
  },
  "commands": {
    "analyze": ["python", "analysis/run.py"]
  },
  "paper": {
    "main": "paper/main.tex",
    "engine": "xelatex",
    "jobname": "paper"
  },
  "quality": {
    "target_total_pages": [32, 40],
    "target_body_pages": [26, 34],
    "max_appendix_body_ratio": 0.25,
    "minimum_score": 85,
    "minimum_figures": 8,
    "required_figure_roles": ["data", "method", "result", "validation"]
  }
}
```

`problem_type` 允许 `forecasting`、`optimization`、`evaluation`、`mechanism`、`simulation` 和 `hybrid`。页数与图表阈值可按题目调整，但每次调整必须记录在运行清单中。默认正文目标不包含参考文献和附录。

配置中的命令使用参数数组，不执行 shell 拼接，以避免路径转义和命令注入问题。所有路径必须解析到项目根目录之内；越界路径直接 FAIL。

## 7. 结构化证据契约

### 7.1 问题映射

`problem-map.json` 为每个小问提供稳定 ID，至少记录：题意目标、输入、输出、现实约束、数学任务、候选方法、最终方法、验证标准和论文章节。每个小问必须至少关联一个模型、一个结果、一个验证和一个结论。

### 7.2 模型注册表

`model-registry.json` 中每个模型记录：

- 模型 ID 与对应小问；
- 变量、参数、集合、单位和数据来源；
- 目标函数与约束摘要；
- 参数估计方法；
- 求解算法、软件版本、随机种子和停止规则；
- 基线模型或选择该模型的理由；
- 适用条件和已知局限。

### 7.3 结果注册表

`result-registry.json` 中每个关键结果记录：

- 结果 ID、值、单位和允许显示精度；
- 生成脚本、输入文件哈希和输出字段；
- 对应问题、模型和验证 ID；
- 可选的表格或图编号。

最终论文中的关键数字必须来自结果注册表或由其中字段通过已登记公式计算。无法追溯的强结论数字为 FAIL。

### 7.4 结论注册表

`claim-registry.json` 中每条结论记录：结论 ID、正文表述、支撑结果 ID、适用范围、反例或失败情形、对应章节。使用“最优、显著、提高、降低、稳健”等措辞时，必须有相应数值或检验支撑。

### 7.5 图表注册表

`figure-registry.json` 中每张图记录：图 ID、文件、角色、源数据、生成脚本、正文引用标签、支持的结果或结论 ID、彩色与黑白可读性检查。图表角色至少覆盖数据理解、方法结构、主要结果和验证分析；同一数据的重复装饰性绘图不能用于满足数量门槛。

### 7.6 验证注册表

`validation.json` 按题型记录：

- 共同项：量纲、边界、手算小样例、基线比较、敏感性、失败案例；
- 预测类：时间顺序切分、滚动验证、MAE/RMSE、区间或残差；
- 优化类：求解器状态、可行性、最大约束违反、界或最优差距、情景扰动；
- 评价类：指标方向、归一化、权重来源、排序稳定性、权重扰动；
- 仿真类：随机种子、重复次数、置信区间和收敛证据。

## 8. 论文结构与篇幅控制

模板正文固定包含：摘要、问题重述、问题分析、数据处理、假设、符号、总体路线、各小问模型与结果、模型检验、敏感性或稳健性、模型评价、结论与建议。具体章节可合并，但逻辑链不能缺失。

每个核心小问章节采用以下内容契约：

1. 目标与本节输入；
2. 关键假设和变量；
3. 数学推导或建模机制；
4. 求解算法和实现参数；
5. 定量结果；
6. 业务或现实解释；
7. 验证、基线或反例；
8. 本问结论及其适用边界。

LaTeX 主文件必须包含四个标签：

```tex
\label{mm:body-start}
\label{mm:body-end}
\label{mm:appendix-start}
\label{mm:appendix-end}
```

正文结束、参考文献开始和附录开始处使用 `\clearpage`，保证页数边界可计算。CLI 从 `.aux` 中读取标签页码，并结合 `pdfinfo` 生成：总页数、正文页数、参考资料区间、附录页数和附录/正文比。

默认质量门槛：正文 26--34 页、总页数 32--40 页、附录不超过正文的 25%。核心定义、模型推导、主要结果、验证和结论只存在于附录时直接 FAIL。附件中的完整明细、代码清单和超大结果表不计入正文质量。

若正文不足，Skill 只能通过补充有证据的推导、比较、误差分析、稳健性、失败案例或管理解释扩充。禁止通过改变字号、扩大行距、重复文字、重复图表、空白页或附录填充页数。

## 9. 构建流程

`build` 执行以下阶段：

1. `validate-config`：校验配置、路径和工具可用性；
2. `inventory`：记录输入文件哈希、大小、类型和数据概况；
3. `analyze`：执行题目专用分析命令；
4. `validate-artifacts`：校验六类 JSON 契约和相互引用；
5. `compile-pass-1`：第一次 XeLaTeX 编译；
6. `compile-pass-2`：第二次 XeLaTeX 编译并稳定交叉引用；
7. `page-metrics`：读取 PDF 与 `.aux`，计算篇幅结构；
8. `static-audit`：审查日志、引用、标签、图表、正文结构和注册表；
9. `render-preview`：渲染所有页面缩略图和可疑页面原图；
10. `report`：生成 JSON 与 Markdown 质量报告和运行清单。

若 `commands.analyze` 为空，`build` 不执行求解，但仍要求已有契约通过校验。任何阶段失败时停止后续依赖阶段，保留日志和已生成产物。

## 10. 质量门禁

### 10.1 硬门禁

以下任一项导致 FAIL，不能 `package`：

- 配置无效、输入缺失或路径越界；
- 分析命令失败；
- 关键契约缺失、JSON 无效或 ID 引用断裂；
- 关键结果无来源，或结论无结果与验证支撑；
- 验证报告显示约束违反、数据泄漏或核心指标无效；
- LaTeX 无法连续编译两次；
- 存在未定义引用、未定义 citation、缺图或致命错误；
- PDF 不存在、不是 A4 或页数标签不可解析；
- 正文低于配置下限；
- 附录/正文比超过配置上限；
- 核心模型、结果或验证仅出现在附录；
- 包含未替换占位符，如 `TODO`、`TBD`、`待补充`、`XX`；
- 最终文件名与当前构建哈希不匹配。

### 10.2 警告项

- Overfull box 不超过 2 pt 时 WARN，超过 2 pt 时 FAIL；
- 图片为低分辨率栅格、字体未嵌入或黑白不可读；
- 存在未引用图表、未使用文献或未引用公式；
- 图表角色不完整或图表数量低于配置；
- 缺少基线、敏感性、失败案例或局限性中的非核心项；
- 章节字数极端失衡、连续页面大面积空白；
- 总页数超出目标但正文与证据完整。

### 10.3 软评分

质量报告按 100 分计算：问题覆盖 10、数据与可追溯性 10、模型严谨性 20、验证与稳健性 20、结果与结论证据 15、正文表达 10、图表 10、LaTeX 5。软评分不抵消硬门禁。默认放行要求无 FAIL 且总分至少 85。

自动评分只反映结构和证据完整性。Skill 必须另外完成一次人工审稿清单，评价假设现实性、模型是否真正回答题意、创新是否有必要、结论是否过度、引用是否支持论断、图表是否讲清楚结果。

## 11. 运行记录与失败恢复

每次命令生成唯一 `run-id`，格式为 UTC 时间加输入哈希短码。运行清单记录：命令参数、环境版本、输入哈希、配置快照、每阶段开始与结束时间、退出码、产物路径、警告和错误。

阶段状态为 `PENDING`、`RUNNING`、`SUCCESS`、`FAILED`、`SKIPPED`。恢复运行根据输入和配置哈希复用无变化的成功阶段；题目输入、分析代码、配置或上游产物变化时，所有依赖阶段失效并重跑。历史运行记录只新增，不覆盖。

`build/paper.pdf` 是当前构建的便利副本。正式交付文件名包含项目 ID、页数和构建哈希，例如：

```text
training-001-38p-a1b2c3d4.pdf
```

该规则避免同名 PDF 缓存导致用户打开旧版本。`package` 同时输出清单，记录 PDF SHA-256、页数、正文页数和源代码哈希。

## 12. 错误处理

- 输入解析失败：生成材料清单和人工修正提示，不伪造题意。
- 可选数据依赖缺失：记录 WARN 并退化为文件级审计。
- 分析不可行：保留求解器日志和验证诊断，禁止写“最优解”。
- 结构化结果缺字段：准确列出 JSON 路径和缺失字段。
- 编译失败：保留两次编译日志和最后成功 PDF，不覆盖正式包。
- 页数边界缺失：FAIL，并指出应添加的 LaTeX 标签。
- 视觉审查未完成：质量报告标为 `NEEDS_MANUAL_REVIEW`，不能宣称最终可提交。

所有错误信息包含阶段、文件、规则 ID、原因和建议修复动作。CLI 不吞掉子进程标准输出或错误输出。

## 13. Skill 内容组织

`SKILL.md` 保持精简，只包含触发条件、核心工作流、强制门禁、CLI 快速入口和参考路由。详细内容分到一级 `references/`：

- `workflow.md`：端到端工作流和迭代节奏；
- `evidence-contracts.md`：六类 JSON 契约；
- `paper-architecture.md`：正文结构、篇幅预算和摘要写法；
- `model-validation.md`：按题型的验证矩阵；
- `quality-gates.md`：规则编号、评分和人工审稿；
- `figure-system.md`：图表角色、风格和证据登记；
- `forecasting.md`、`optimization.md`、`evaluation.md`：题型专用路线。

`assets/` 保存可复制的项目骨架和 LaTeX 模板，`scripts/` 保存 CLI 与核心模块，`tests/` 保存单元和端到端样例。`vendor/` 仅作为参考来源，不进入默认运行路径。

## 14. 测试策略

### 14.1 单元测试

使用 Python 标准库 `unittest` 覆盖：配置校验、路径边界、哈希、JSON 契约、ID 交叉引用、LaTeX 日志解析、`.aux` 页码解析、正文/附录比例、评分、唯一文件名和运行清单。

每个新行为先编写失败测试，再实现最小代码，最后重构。

### 14.2 集成测试

建立最小可编译 fixture，验证：

- `init` 创建完整且不含题目数字的工程；
- 对非空目录不覆盖已有文件；
- `audit` 能发现占位符、断裂 ID、缺图和过重附录；
- `build` 连续编译并输出唯一 PDF；
- 相同输入重复运行产生相同内容哈希；
- 修改输入后旧阶段失效；
- 失败时保留清单和日志。

### 14.3 三类题型端到端验证

1. 优化类：采用现有 `traning1` 作为真实工程，接入其 MILP、结果和 38 页论文，验证 adopt、证据注册、正文比例和唯一 PDF。
2. 预测类：使用小型确定性时间序列 fixture，生成训练/验证指标、预测图和可编译短论文；验证滚动评估契约。
3. 评价类：使用小型多指标 fixture，生成归一化、权重、排序与权重扰动；验证排序稳定性契约。

端到端验收不要求两个 fixture 达到 35 页，但必须通过其测试配置中的正文与附录门槛。真实 `traning1` 必须通过高水平配置。

### 14.4 Skill 前向测试

在无 Skill 基线之外，使用新 Skill 分别完成新题启动、论文审稿和正文失衡修复任务。比较是否稳定地产生标准工程、证据链和门禁报告，并检查是否仍会把总页数误当作正文页数。

## 15. 迭代阶段

### 第一轮：可靠骨架

实现 CLI、配置、初始化、adopt、运行清单、契约校验、LaTeX 编译和基础审查。将当前 Skill 改为可调用框架的协调层。

### 第二轮：质量门禁

实现正文/附录页数、图表注册、结果—结论链、评分报告、唯一 PDF、页面预览和人工审稿清单。接入 `traning1` 并修复所有真实阻断项。

### 第三轮：题型泛化

补充预测和评价 fixture、题型参考、验证契约和端到端测试。使用前向测试修订 Skill 中容易被跳过或误解的规则。

### 第四轮：发布审计

从空目录运行新题初始化，从现有项目运行 adopt，从三类样例运行 build/audit/package；检查输入未被修改、结果可追溯、PDF 唯一、门禁覆盖真实要求。只有全部证据通过后，框架才可标记为搭建成功。

## 16. 验收清单

框架完成必须同时满足：

- 自然语言 Skill 与 CLI 双入口可用；
- 新项目和已有项目均可接入；
- 原始题目与附件不被修改；
- 六类证据契约可校验并相互追踪；
- 题目专用分析可由统一命令执行；
- LaTeX 可连续编译并生成唯一 PDF；
- 总页数、正文页数和附录页数分别核验；
- 正文不足或附录过重会阻断发布；
- 日志、引用、图表、占位符和关键结果受到检查；
- 质量报告同时提供硬门禁、软评分和人工审稿项；
- 优化、预测和评价三类端到端样例通过；
- 当前 `traning1` 真实项目通过高水平配置；
- Skill 通过无 Skill/有 Skill 对照的前向测试；
- 所有测试、编译和发布审计均有新鲜命令输出作为证据。
